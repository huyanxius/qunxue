# 架构决策（只追加）

## 2026-07-28 沿用现有协作仓库

背景：原仓库已配置团队权限，且远端 `main` 没有合入旧 LiveDemo 实现。
决定：正式工程从最新 `main` 建分支，保留历史、产品文档与训练资料，但不复用旧 LiveDemo 代码、资产和依赖。
代价：旧演示能力不计入正式实现进度，所有能力按新契约重新验收。

## 2026-07-28 首个架构增量

背景：一次实现全部领域、模型运行和页面会让架构不可审查。
决定：先跑通 React → 生成 SDK → FastAPI → 业务模块 → repository port → SQLite 的最小链路，其余模块先冻结公共契约和门禁。
代价：完整状态机、模型 Schema、可靠异步恢复和真实主链分别进入后续增量。

## 2026-07-28 技术栈

背景：工程需要可运行、可生成契约，并允许替换外部模型和知识服务。
决定：采用 React/Vite/TanStack Query、FastAPI/Pydantic、SQLAlchemy/Alembic/SQLite，并从 OpenAPI 生成前端 SDK。
代价：当前只服务本地单实例演示；认证、多用户、生产数据库和可靠任务执行器另行设计。

## 2026-07-28 业务模块边界

背景：技术分层不足以说明哪些业务代码共同变化、模块对外开放什么。
决定：后端拆为研究入口、知识目录、理论匹配、研究框架；前端拆为 SocioMatch 工作区和知识浏览器。跨模块只走公共入口与不可变快照。
代价：检索、模型和异步执行暂作消费模块拥有的窄端口，出现第二个稳定实例后再评估独立模块。

## 2026-07-28 契约与运行边界

背景：手写双份 DTO 容易漂移，内联执行也不能冒充可靠队列。
决定：Pydantic 生成 OpenAPI 与 TypeScript；首期同步完成，SQLite 仅限单实例本地演示。
代价：真实异步运行需另行实现 dispatcher、lease、heartbeat、重试预算和启动恢复。

## 2026-07-28 模块交接与人工门禁

背景：只传 ID 会迫使下游跨库读取；记录用户点击也不等于满足正式采用条件。
决定：跨模块传带版本与来源的完整快照；理论决定区分记录、确认和暂缓；阻断审校修改后生成新版本再审。
代价：快照体积增加，完整门禁真值表仍需在领域契约 Issue 中冻结。
